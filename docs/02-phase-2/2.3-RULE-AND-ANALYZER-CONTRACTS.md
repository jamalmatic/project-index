# Phase 2.3 — Rule and Analyzer Contracts

**Status: COMPLETE / LOCKED**

Phase 2.3 establishes the executable capability boundary for detection rules and analyzers. It does not introduce parser-specific implementations, persistence coupling, dynamic package loading, or production scheduling.

## Delivered contracts

### 1. Rule Definition Contract

Rules have stable identity/version metadata, explicit names/descriptions, declared capabilities, and deterministic execution semantics. Invalid identity metadata and duplicate capabilities are rejected.

### 2. Analyzer Contract

Analyzers have stable identity/version metadata, names, optional descriptions, declared capabilities (`syntax`, `structure`, `semantics`, `metadata`), and a typed execution boundary. Analyzer exceptions are converted into structured failures rather than escaping the execution boundary.

### 3. Plugin Boundary

Rules and analyzers are represented through a common plugin boundary with explicit plugin identity, version, name, kind, capabilities, and implementation. Plugin kind must match the implementation kind.

### 4. Registration and Capability Discovery

The in-process registry provides stable registration by plugin ID, duplicate protection, lookup, kind discovery, capability discovery, immutable registration manifests, capability indexes, and extraction of registered rules/analyzers.

### 5. Deterministic Orchestration

Registered analyzers can be selected by capability and executed independently. Analyzer execution is isolated, observations and failures are normalized into deterministic ordering, and batch execution has stable resource ordering.

## Implemented package surface

The Phase 2.3 implementation lives in `packages/validation`:

```text
rule.ts
analyzer.ts
plugin.ts
registry.ts
orchestration.ts
```

Each contract has focused tests. The package index exports the complete Phase 2.3 surface.

## Execution boundary

```text
DiscoveryResource
      |
      v
DetectionMatch
      |
      v
PluginRegistry
      |
      +---- capability selection
      |
      v
AnalyzerContract(s)
      |
      v
Deterministic orchestration
      |
      +---- AnalysisObservation
      +---- AnalyzerFailure
```

Rules and analyzers remain independent of persistence. The orchestration layer consumes discovery values and produces analysis values; it does not persist them.

## Determinism guarantees

- plugin lookup is keyed by stable identity;
- analyzer selection is sorted by analyzer ID/version;
- analysis observations are sorted by analyzer identity/version/kind;
- failures are sorted by analyzer identity/message;
- analysis batches are sorted by resource URI;
- analyzer exceptions become structured failures;
- returned contract values are immutable where required by the model.

## Explicit non-goals

Phase 2.3 does not claim:

- parser-specific analyzers;
- dynamic filesystem/package plugin loading;
- plugin lifecycle management;
- compatibility negotiation between plugin versions;
- distributed scheduling;
- persistence of analysis observations;
- a production plugin marketplace/service.

Those concerns remain future work unless explicitly promoted by a later phase.

## Acceptance
