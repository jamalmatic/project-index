# Phase 2.2 — Discovery Primitives

Status: **COMPLETE / LOCKED**

## Objective

Provide a deterministic, read-only discovery boundary that identifies resources without coupling discovery to a filesystem API, parser, language analyzer, or persistence implementation.

## Contract

Discovery has these conceptual stages:

```text
provider
  ↓
resource normalization
  ↓
deterministic ordering
  ↓
detection rules
  ↓
discovery observations
  ↓
normalization
  ↓
Phase 2.1 ingestion
```

### Resource

A discovered resource has:

- a stable discovery resource ID;
- a normalized URI;
- an explicit resource kind (`file`, `directory`, `url`, or `other`).

Discovery resource identity is not automatically a domain Entity identity.

### Provider boundary

A `DiscoveryProvider` supplies discovered resources through a read-only `discover()` operation. The contract does not prescribe filesystem traversal, URL fetching, repository APIs, or parser implementations.

### Determinism

Discovery results are normalized and returned in deterministic URI order. Rule execution and discovery observations also have deterministic ordering. Provider ordering must not become semantic ordering.

### Detection rule boundary

A `DetectionRule` has:

- a branded rule ID;
- an explicit version;
- a resource-scoped execution context;
- structured matches;
- structured failures.

A rule failure is isolated from other rules and represented as a failed discovery observation rather than silently disappearing or aborting the complete discovery run.

### Observation

A `DiscoveryObservation` records the result of applying a detection rule to a resource. It retains:

- resource identity;
- detection rule identity and version;
- status (`matched`, `unmatched`, or `failed`);
- detected kind/value where applicable;
- captured properties;
- structured failure information when applicable.

Observations are immutable and have deterministic identifiers/order.

### Normalization boundary

Discovery observations are converted by `normalizeDiscovery()` into canonical ingestion inputs. This boundary is deliberately conservative:

- it performs no persistence;
- it does not invent entities, assertions, or relationships;
- a generic observation is not forced into domain Evidence unless it has a valid canonical target under the existing Evidence contract;
- accepted domain inputs continue through Phase 2.1 validation and atomic persistence.

### Evidence

Discovery evidence records why a resource was observed and may carry source identity, path, excerpt, and arbitrary capture metadata.

Discovery evidence is deliberately distinct from domain `Evidence`: the current domain Evidence model requires an assertion or entity target. A discovered resource does not become a knowledge entity merely because it was observed.

### Read-only semantics

Discovery must not mutate project contents or knowledge persistence. It returns observations; ingestion is responsible for turning accepted observations into persisted knowledge.

## Current implementation

The validation package provides:

- `DiscoveryResourceId` and canonical ID construction;
- `DiscoveryResource` and `DiscoveryInput`;
- `DiscoveryProvider`;
- deterministic `discover()` orchestration;
- `DetectionRuleId` and versioned `DetectionRule`;
- structured `DetectionMatch`, `DetectionRuleFailure`, and `DetectionRuleResult`;
- deterministic rule execution and failure isolation;
- `DiscoveryObservation` and immutable observation factories;
- `runDiscovery()` and deterministic batch discovery;
- `normalizeDiscovery()` as the discovery → ingestion boundary;
- unit, contract, transaction, and end-to-end integration coverage.

## Acceptance

Phase 2.2 is locked because the following acceptance conditions are satisfied:

1. resource normalization is deterministic;
2. discovery does not mutate the inspected project or knowledge persistence;
3. provider ordering cannot change returned semantic ordering;
4. detection results are structured and rule failures are explicit;
5. discovery observations retain rule identity/version and resource identity;
6. discovery orchestration feeds the Phase 2.1 ingestion boundary without coupling it to a parser or filesystem implementation;
7. normalization respects the existing Evidence contract and strict optional-property semantics;
8. typecheck, tests, and CI are green.

## Explicit non-goals

- filesystem traversal implementation;
- language parsing;
- parser-specific analyzer implementations;
- persistence of discovered resources as domain entities;
- inference;
- query APIs;
- plugin registry/lifecycle management;
- distributed scheduling or production-scale discovery.

## Lock rule

This document is the locked Phase 2.2 contract. Changes that alter resource identity, detection semantics, observation semantics, normalization boundaries, or read-only guarantees require an explicit source-of-truth update and, where architectural, an ADR. Phase 2.3 must build on this contract rather than silently redefining it.
