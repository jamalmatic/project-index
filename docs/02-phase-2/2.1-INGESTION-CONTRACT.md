# Phase 2.1 — Ingestion Contract

Status: **COMPLETE / LOCKED**

## Objective

Turn arbitrary normalized input into canonical Project Index domain objects while preserving source, evidence, provenance, validation, and atomic persistence semantics.

Phase 2.1 is the completed capability contract. Parsers, filesystem discovery, language-specific analyzers, and external connectors remain out of scope.

## Implemented contract

An ingestion operation has these stages:

```text
input
  ↓
normalize / construct
  ↓
canonical domain objects
  ↓
evidence + provenance construction
  ↓
complete-batch validation
  ↓
staged-reference resolution
  ↓
atomic persistence
  ↓
single commit
```

### Input

Input identifies the source/resource being ingested and the domain objects to construct. The ingestion boundary does not require a particular parser, transport, filesystem API, or database.

### Canonicalization

Ingestion creates domain values through the existing domain/evidence factories. Callers do not bypass normalization or branded IDs by supplying structurally compatible persistence objects.

### Evidence

Ingested evidence retains source identity and the available locator/reference metadata. Evidence references are validated before persistence.

### Provenance

Ingestion constructs provenance metadata connecting resulting knowledge to its source/evidence. Provenance is explanatory metadata, not a substitute for evidence.

The current ingestion result preserves constructed provenance. Independent provenance persistence is deliberately not claimed because the current `UnitOfWork` contract does not expose a provenance repository.

### Validation

Validation runs before persistence. The writer prepares the complete batch first, collects validation issues, and does not mutate repositories when the batch is invalid.

References can target objects already persisted in the `UnitOfWork` or objects staged earlier in the same ingestion batch. This allows valid source/entity/assertion/relationship/evidence chains to be ingested atomically without prematurely writing partial state.

### Persistence

A multi-object ingestion operation is atomic with respect to the supplied `UnitOfWork`:

- all prepared writes commit together;
- no repository save occurs before complete-batch validation succeeds;
- validation failure performs no commit and no partial persistence;
- persistence failure rolls the unit of work back;
- successful batches perform one commit;
- the caller receives the structured validation result or original persistence error.

## Determinism

For the same normalized input and equivalent repository state, ingestion produces equivalent canonical values and equivalent validation outcomes. Runtime timestamps are metadata and must not change semantic identity.

## Acceptance results

Phase 2.1 is accepted and locked. Tests demonstrate:

1. normalized input creates canonical immutable domain values;
2. source/evidence are retained;
3. provenance connects the resulting knowledge to its evidence in the ingestion result;
4. invalid references prevent persistence;
5. references between objects in one batch resolve through staged state;
6. multiple objects commit atomically;
7. persistence failure rolls back the complete ingestion/write transaction;
8. invalid batches leave repository state unchanged;
9. successful batches commit exactly once.

The duplicate-policy requirement remains an explicit future contract rather than an implicit behavior. Repeated ingestion must not be described as having a finalized duplicate policy until that policy is implemented and tested.

## Tests

The Phase 2.1 implementation is covered by validation package unit/integration tests, including:

- ingestion success and provenance preservation;
- invalid-reference rollback;
- complete-batch atomicity;
- persistence failure rollback;
- single-commit transaction semantics;
- intra-batch staged-reference resolution.

The full repository test/CI gate is green for the locked Phase 2.1 implementation.

## Explicit non-goals

- filesystem/project discovery;
- language parsing;
- analyzer/plugin execution;
- inference or derivation beyond recording provenance;
- query APIs;
- external connector protocols;
- independent provenance persistence;
- finalized duplicate/idempotency policy.

Those capabilities begin in later Phase 2 steps or require an explicit future contract.

## Change control

Phase 2.1 is locked. Changes to its atomicity, validation-before-persist, staged-reference, or transaction semantics require an explicit architectural decision and corresponding test updates. CI must remain green at the phase boundary.
