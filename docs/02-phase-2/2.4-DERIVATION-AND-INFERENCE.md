# Phase 2.4 — Derivation and Inference

**Status: COMPLETE / LOCKED**

## Purpose

Phase 2.4 establishes the executable derivation boundary on top of the Phase 1 assertion, evidence, provenance, and persistence models and the Phase 2.3 rule/analyzer contracts.

## Implemented contract

A derivation is an explicit, immutable lineage record connecting:

- one derived/output assertion;
- one or more input assertions;
- zero or more evidence records;
- a stable rule identity and version;
- optional activity and recording metadata.

Derivation execution requires at least one input assertion. Input assertion IDs are preserved deterministically and duplicate input assertion IDs are rejected by the domain derivation factory.

## Execution boundary

The validation package provides a derivation rule contract and execution path:

```text
input assertions + evidence
        ↓
   DerivationRule
        ↓
 derived Assertion
        ↓
   Derivation record
        ↓
  Provenance record
        ↓
    UnitOfWork
        ↓
      commit()
```

Rules have explicit `id` and `version` metadata. The persisted derivation rule identity is represented as `ruleId@version` so the exact rule revision responsible for a result remains inspectable.

## Atomic persistence

Derived assertions, derivations, and provenance are persisted through the same `UnitOfWork` transaction.

The orchestration guarantees:

1. the derived assertion is constructed before persistence;
2. the derivation record references the exact output assertion and its inputs;
3. provenance references the derived assertion and carries derivation/input/evidence lineage metadata;
4. all three records are saved before commit;
5. successful execution performs exactly one commit;
6. persistence or commit failure triggers rollback;
7. a failed derivation does not produce a committed partial lineage.

The in-memory implementation is the reference behavioral implementation for transaction semantics; PostgreSQL participates in the same UnitOfWork contract.

## Determinism

Deterministic end-to-end tests verify that identical derivation inputs and rule versions produce identical assertion, derivation, and provenance values. The execution contract does not introduce nondeterministic ordering or hidden persistence side effects.

## Package responsibilities

- `packages/evidence/` owns the domain `ProvenanceRecord` and `Derivation` models and their factories.
- `packages/validation/` owns derivation rule execution and atomic persistence orchestration.
- `packages/storage/` owns repository ports and UnitOfWork transaction boundaries, including derivation and provenance repositories.
- `packages/domain/` owns assertion construction.

## Non-goals

Phase 2.4 does not claim:

- a general-purpose probabilistic inference engine;
- automatic theorem proving;
- distributed inference scheduling;
- background derivation workers;
- rule marketplace or dynamic plugin loading;
- conflict-resolution policy beyond existing validation behavior;
- production-scale performance guarantees.

## Acceptance

Phase 2.4 is **COMPLETE / LOCKED** after implementation, deterministic end-to-end tests, typecheck, test-suite acceptance, and CI verification.

Future changes that alter the derivation rule, lineage, provenance persistence, or atomic transaction boundary require an explicit source-of-truth update and, where architectural, an ADR.
