# Phase 2.4 — Derivation and Inference

**Status: ACTIVE**

## Purpose

Phase 2.4 turns validated observations and existing assertions into explicitly derived assertions whose origin can be inspected and replayed.

This phase builds on the locked Phase 1 provenance/derivation model and the locked Phase 2.3 rule/analyzer contracts.

## Scope

### 1. Explicit derivation execution contract

A derivation records:

- a stable derivation ID;
- the output assertion ID;
- the input assertion IDs;
- supporting evidence IDs;
- the rule ID responsible for the derivation;
- optional activity identity and recording metadata;
- immutable properties.

### 2. Rule/activity identity

Every derived assertion must identify the rule that produced it. When execution is represented as an activity, the activity identity must remain inspectable independently of the assertion payload.

### 3. Derived assertion creation

Derived assertions are ordinary domain assertions. Their derived status must come from their provenance/derivation chain rather than from an ad-hoc flag that bypasses the assertion model.

### 4. Lineage

A derivation must retain enough lineage to answer:

- which assertions were inputs;
- which evidence supported the derivation;
- which rule produced the result;
- which activity recorded the derivation when available.

### 5. Persistence

Derivation/provenance records must be persisted atomically with the derived assertion. A derived assertion without its required lineage is not a successful Phase 2.4 result.

### 6. Determinism

Given the same validated inputs, rule identity/version, and execution context, derivation output and lineage ordering must be deterministic.

## Non-goals

Phase 2.4 does **not** implement:

- probabilistic inference;
- machine-learning model training;
- a general-purpose logic programming engine;
- distributed inference scheduling;
- snapshot publication;
- query APIs;
- production plugin loading;
- conflict resolution policy beyond preserving explicit derivation lineage.

## Architectural boundary

```text
Discovery / Analyzer observations
            ↓
     validated assertions
            ↓
       derivation rule
            ↓
      derived assertion
            ↓
   derivation + provenance
            ↓
      atomic persistence
```

Inference must not bypass the existing validation and persistence boundaries.

## Acceptance gate

Phase 2.4 can be locked only when every derived assertion has an inspectable derivation chain back to its input assertions/evidence, derivation records are persisted atomically, and deterministic tests pass under CI.
