# Phase 2.5 — Validation Profiles and Conflict Handling

**Status: COMPLETE / LOCKED**

## Purpose

Phase 2.5 turns the existing validation primitives into a reusable profile-driven validation boundary with explicit conflict handling and durable conflict decisions.

The phase is intentionally deterministic. A conflict is never silently converted into an accepted fact.

## Implemented boundary

```text
ValidationProfile
  → validation rules
  → ValidationResult
  → conflict detection
  → explicit ConflictResolutionPolicy
  → ConflictResolution
  → ConflictDecisionRecord
  → transactional persistence
  → UnitOfWork commit
```

On persistence failure:

```text
persistence failure
  → UnitOfWork rollback
  → original error propagated
  → no successful commit
```

## Contracts

### Validation profile

A profile gives a stable name/identity to a deterministic set of validation rules and is executed through the existing validation orchestration.

### Validation conflict

A conflict is created when multiple distinct rules report issues for the same validation subject.

Conflict identity is deterministic:

```text
validation-conflict:<subjectId>:<sorted-rule-ids>
```

The conflict records:

- subject identity;
- conflict severity (`error` or `warning`);
- participating rule IDs;
- original validation issues.

### Resolution policy

Resolution is explicit and represented separately from validation.

Current policies:

| Strategy | Meaning |
|---|---|
| `reject` | Keep the conflict unresolved. |
| `accept-first` | Select the first deterministic rule. |
| `accept-last` | Select the last deterministic rule. |

The selected rule is recorded only for resolving strategies.

### Durable decision

A `ConflictDecisionRecord` combines the immutable conflict representation with the resolution decision so that the decision can be persisted and inspected later.

### Persistence

The persistence repository deliberately exposes only:

```ts
save(record): Promise<void>
```

Batch atomicity belongs to the surrounding `UnitOfWork`; a separate `saveMany` contract is intentionally not introduced.

## Public API

Consumers use the public workflow instead of assembling internal components manually:

```ts
validateAndPersist(subject, unitOfWork, {
  profile,
  conflictPolicy,
  conflictDecisions,
});
```

The public workflow coordinates:

1. profile execution;
2. conflict detection;
3. explicit conflict resolution;
4. serialization;
5. transactional persistence;
6. commit/rollback.

## Explicit non-goals

Phase 2.5 does not claim:

- probabilistic conflict resolution;
- human review workflows;
- distributed conflict resolution;
- external policy services;
- automatic selection of facts from unresolved conflicts;
- production governance/certification infrastructure;
- performance or scaling guarantees.

## Architectural rule

**Validation result, conflict, and resolution are three different concepts.**

A validation result describes what rules reported. A conflict describes competing rule outcomes. A resolution records an explicit policy decision. The implementation must preserve these distinctions.
