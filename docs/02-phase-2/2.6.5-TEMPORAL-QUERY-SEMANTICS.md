# Phase 2.6.5 — Temporal Query Semantics Decision

**Status: LOCKED DECISION / IMPLEMENTATION BLOCKED**

## Decision

Phase 2.6.5 will not introduce an independent temporal model in the storage/query layer.

Temporal query behavior MUST consume the authoritative domain temporal contract (`TemporalContext`) once that contract is available in the source tree.

Storage code MUST NOT independently invent or encode semantics such as:

```text
validFrom <= queryTime < validTo
```

unless that exact rule is established by the authoritative domain contract.

## Why

The domain model references temporal context on temporal knowledge objects, but the current repository state does not expose a retrievable `TemporalContext` definition, constructor, or test suite. Repository searches for `TemporalContext`, `temporal`, `validFrom`, and `validTo` returned no authoritative implementation.

Implementing temporal filtering before recovering that contract would create a second semantic model and could make persistence behavior incompatible with the intended domain model.

## Required future boundary

```text
Authoritative TemporalContext
          |
          v
     temporal matcher
          |
          v
      QueryService
          |
   +------+------+------+
   |             |      |
 Entity       Assertion Relationship
```

The query layer may expose temporal filtering, but matching semantics belong to the domain temporal contract, not to PostgreSQL, the in-memory repository, or an ad-hoc query utility.

## Rules locked for implementation

1. **No duplicate temporal model.** Do not add `validFrom`, `validTo`, or a competing interval type solely for Phase 2.6.5.
2. **No storage-defined semantics.** Memory and PostgreSQL implementations must use the same domain-level matching semantics.
3. **Untemporally-qualified records are not implicitly invalid.** Absence of temporal qualification must not be treated as a validation failure or silently deleted from ordinary reads.
4. **Explicit temporal queries are opt-in.** Ordinary queries remain non-temporal unless a temporal criterion is supplied.
5. **Deterministic ordering remains mandatory.** Temporal filtering must preserve the existing canonical-ID ordering guarantee.
6. **Contract recovery precedes implementation.** The authoritative `TemporalContext` definition and tests must be restored/located before the temporal matcher or query API is implemented.

## Acceptance gate

Phase 2.6.5 cannot be marked complete until:

- the authoritative temporal type is present;
- its semantics are documented and tested;
- the query contract consumes that type;
- memory and PostgreSQL behavior agree;
- boundary cases are covered by tests;
- `pnpm typecheck` and `pnpm test` are green.

## Explicit non-goals

- no SQL-specific temporal API;
- no new temporal persistence schema;
- no temporal query language;
- no inferred time semantics;
- no changes to existing domain temporal meaning without an explicit source-of-truth decision.
